# Parallel continuation

`start_session(..., threads=4)` now advances independent chains concurrently in a bounded session-local pool. The default remains1. Supported metrics remain identity/diagonal; chain rescue remains unsupported. The native callback and user_data must satisfy the existing deterministic, reentrant, thread-safe CFunc contract.

A coordinator owns the target and borrowed chain states; a scoped Rayon pool is joined before target/DLL ownership can be released. Initialization and shared initial-step search retain their original order. Each chain retains its own RNG, adaptation, metric and transition position between chunks. All tasks finish before a request publishes a chunk or terminal error. Cancellation remains cooperative: a nonreturning native callback cannot be forcibly interrupted. Close from the coordinator or one of its callback threads cancels and reports an error instead of joining itself. Progress remains a completed-request/error snapshot, and the prototype retains bounded full history rather than constant-memory streaming.

Correctness validation with Rust1.88.0-x86_64-pc-windows-gnu:11 session tests,15 sampler API tests and2 existing kernel fingerprint tests pass. Session tests compare four-chain1vs4-thread runs and uneven chunks exactly, including all transition diagnostics, metrics, tuning and cumulative callback counts. A barrier proves four simultaneous callbacks; cancellation joins them before target drop. Parallel target errors/panics and reentrant close are terminal without self-deadlock. The callback budget test verifies accounting under a roomy worst-case bound, not an exhaustion-contention stress test.

An isolated debug Python extension passes6 public-session tests, including all9 serialized diagnostic fields and ordinary-sample identity for threads1/4 with caches enabled/disabled. No attested production runtime was replaced. These are correctness results, not throughput evidence; a release-build latency comparison is still required.
